# Правила работы — личный каталог фильмов

## О проекте

Учебный сайт для поиска фильмов и ведения личного каталога с телефона и компьютера. Объясняй начинающему простыми словами, работай небольшими проверяемыми шагами.

Предлагаемый стек: HTML, CSS, JavaScript; серверная функция Node.js на Vercel. Стек пока предложен для согласования. Источник фильмов — https://kinopoiskapiunofficial.tech/ . Интернет и необходимые зависимости разрешены.

## Первая версия

- Поиск по названию только по кнопке «Найти», без запросов на каждую букву.
- Карточки: постер, название, год, рейтинг API. Отсутствующие данные заменять понятными подписями.
- Списки «Хочу посмотреть» и «Просмотрено»; не допускать повторного добавления по ID фильма во всём каталоге. Перенос между списками меняет статус существующей записи.
- Личная оценка — целое число от 1 до 10; отзыв — до 500 символов. Оценка API и личная оценка подписаны отдельно.
- Личный каталог сохраняется в localStorage. Нет регистрации, базы данных и синхронизации устройств. Очистка данных браузера удаляет каталог.
- Понятные отдельные сообщения при ошибке сети, отсутствии результатов и исчерпании лимита API.
- Русский интерфейс, работа на ширине 375px без горизонтальной прокрутки. Высота полей от 44px, область нажатия кнопок минимум 44 × 44px. Подписи полей, видимый фокус и управление с клавиатуры.

## Секреты и сервер

- Браузер обращается к своей серверной функции; только она обращается к Kinopoisk API Unofficial.
- Ключ хранить только в серверной переменной окружения KINOPOISK_API_KEY. Локально — в игнорируемом .env.local, на хостинге — в настройках окружения.
- Не просить ключ в чате, не выводить его в терминал, логи, ответы сервера, клиентский код, документацию, тестовые данные или Git. Не использовать публичные префиксы переменных для ключа.
- .env.example содержит только пустую переменную. Настоящий ключ пользователь вводит самостоятельно.
- Сервер проверяет параметры запроса, обращается только к фиксированному API и возвращает только необходимые данные. Ошибки очищать от заголовков и секретов. Не делать бесконечных повторных запросов.
- Перед публичным запуском проверить ограничения частоты запросов к своей функции и обработку квоты API, чтобы посетители не расходовали её бесконтрольно.

## Порядок работы

- Каждую новую функцию начинать с specs/NNN-nazvanie.md: следующий номер из трёх цифр и название латиницей через дефис.
- Обязательные разделы: «Для кого и зачем», «Что должно быть», «Примеры», «Ограничения», «Готово, когда».
- До пользовательского «делай» код приложения не писать. Подготовка документов и файлов защиты секретов разрешена текущим запросом.
- Большую функцию разбивать на шаги с флажками, результатом и ручной проверкой каждого. Выполнять один шаг, проверять и останавливаться для проверки пользователем. Не считать разрешение на коммит разрешением на следующий шаг.
- После завершения функции обновлять возможности и проверки в README.md. Отличать план от работающего и проверенного поведения.
- Разделы README о личном опыте и отчёте заполняет пользователь. Не придумывать за него ошибки, впечатления или результаты.
- При исправлении сначала объяснить причину, затем внести ограниченную правку и проверить её. Не менять несвязанные файлы.
- После работы сообщать: изменённые файлы, выполненные проверки, что не проверено и что проверить пользователю.

## Git и публикация

- Код должен оказаться в публичном репозитории GitHub; работающий сайт — на хостинге с серверными функциями. Реальные ссылки добавить в README после создания и проверки.
- В начале работы проверять наличие репозитория и git status. Чужие изменения сохранять; при конфликте с задачей уточнять дальнейшие действия.
- Коммит и push — только после проверки пользователем и ответа «да» на конкретный набор изменений. Автоматический коммит после тестов запрещён.
- Перед коммитом проверить diff, список подготовленных файлов и отсутствие секретов в них. Не печатать значения секретов при проверке. Добавлять файлы явными путями, не использовать git add .
- Не переписывать историю Git и не выполнять разрушительных команд. Не применять принудительный push и сброс с потерей изменений.
- Если репозитория или remote нет, сообщить об этом; не заявлять, что изменения опубликованы. При ошибке коммита или push объяснить её и не обходить защиту.
